## 1. Резюме (Executive Summary)

Операторы контакт-центра вручную определяют тематику входящих обращений из чата и почты и перекладывают их между очередями. Делаем online-сервис, который классифицирует текст обращения по 24 тематикам и возвращает тематику с уверенностью. Система обработки обращений использует ответ для автоматической маршрутизации. Ожидаемый эффект — снижение доли ручных перекладываний с 35% до 10% и сокращение времени до первого ответа.

## 2. Бизнес-контекст и проблема

- Проблема: около 35% обращений попадает не в ту очередь, среднее время до первого ответа — 47 минут.
- As-is: тематику выбирает дежурный оператор вручную.
- To-be: тематика определяется автоматически при поступлении; при низкой уверенности обращение уходит в общую очередь.
- Связь со стратегией: программа снижения стоимости обслуживания.

## 5. Scope

### 5.1 In Scope
- Классификация текста обращения (чат, почта) по 24 тематикам.
- REST API для системы обработки обращений.

### 5.2 Out of Scope
- Голосовые обращения.
- Автоматические ответы клиенту.

### 5.3 Допущения (Assumptions)
- Справочник тематик стабилен в течение квартала.

### 5.4 Ограничения (Constraints)
- Бюджет: в рамках квоты CPU контакт-центра.
- Сроки: ПЭ до конца Q1 2026.
- Технологический стек: OpenShift, MLflow, GitLab. Закрытый контур, без внешних API (DOC-07).
- Регуляторные: тексты обращений могут содержать ПДн (класс К3).

## 6. Функциональные требования (Functional Requirements)

| ID | Требование | Приоритет | Критерий приёмки (Given/When/Then) |
|---|---|---|---|
| FR-01 | Сервис возвращает тематику и уверенность по тексту обращения | Must | Given текст обращения, When вызван API, Then возвращаются тематика из справочника и уверенность 0..1 |
| FR-02 | При уверенности ниже 0.6 возвращается признак «ручная маршрутизация» | Must | Given уверенность < 0.6, When формируется ответ, Then флаг manual_routing = true |
| FR-03 | Сервис логирует обращения без текста (только ID и тематику) | Should | Given обработан запрос, When пишется лог, Then текст обращения в логе отсутствует |

### 6.1 Пользовательские сценарии / User Stories
- Как оператор, я хочу получать обращения сразу в своей очереди, чтобы не тратить время на перекладывание.

### 6.2 Функциональные требования к ML-компоненту (если применимо)
- Вход: текст до 4000 символов; выход: тематика, уверенность, флаг ручной маршрутизации.
- Тип задачи: многоклассовая классификация текста.
- Инференс: real-time, синхронный вызов.
- Fallback: при ошибке или таймауте — общая очередь.
- Explainability: N/A.

## 7. Нефункциональные требования (Non-Functional Requirements)

### 7.1 Производительность и масштабируемость
| Требование | Целевое значение |
|---|---|
| Latency (p95) | ≤ 300 мс |
| Throughput | 15 RPS в среднем, пик 40 RPS |
| Ресурсы | 2 vCPU, 4 ГБ RAM на реплику, 2 реплики; GPU не требуется |

### 7.2 Доступность и надёжность
- Доступность 99.5% в рабочие часы; при недоступности — fallback в общую очередь.

### 7.3 Данные
- Источник — система обработки обращений; обучающая выборка — 120 тыс. размеченных обращений.

### 7.4 ML-специфичные требования
- Переобучение раз в квартал или при падении macro-F1 ниже 0.78 на контрольной выборке.

### 7.5 Безопасность и приватность
- Данные: тексты обращений, возможны ПДн (класс К3).
- Потоки: система обработки обращений → сервис классификации (OpenShift) → система обработки обращений.
- Конкретные меры безопасности согласовываются отдельно с ИБ.

### 7.6 Наблюдаемость (Observability)
- Метрики: RPS, latency, доля ручной маршрутизации; алерты — дежурному команды ИИ-среды.

### 7.7 Совместимость и интеграции
- REST/JSON, интеграция с системой обработки обращений.

### 7.8 Эксплуатационные требования (Operability)
- Механизм деплоя выбран командой ИИ-среды по внутренней документации (DOC-02).
