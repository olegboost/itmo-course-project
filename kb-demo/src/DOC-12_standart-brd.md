Учебный синтетический документ. Наименования систем, ролей и числовые значения условны.

## A. Правила применения

1. BRD — критерий приёмки задачи по выводу ИИ-модели или ИИ-сервиса. Его готовят по итогам интервью с инициатором до подачи заявки по DOC-01.
2. Заполняются все разделы 0–12. Неприменимые разделы помечаются «N/A», неизвестные значения — «TBD» с обязательным пунктом в разделе 11 «Открытые вопросы».
3. В BRD различаются факты, сказанные инициатором, и рабочие гипотезы интервьюера. Гипотеза попадает в требования только после явного подтверждения инициатором и с пометкой «рабочая гипотеза».
4. Базовое ограничение — закрытый контур: вызовы внешних моделей и API запрещены (DOC-07). Предложения, которые ему противоречат, фиксируются как риск или несоответствие, а не как вариант реализации.
5. Раздел 4 «Стейкхолдеры» заполняется фиксированным набором ролей: Product Owner / инициатор; Инженерия — команда развития ИИ-среды; Инфраструктура — DevOps; Безопасность — ИБ; Data Science / ML.
6. Раздел 7.5 содержит только факты о данных, потоках и чувствительности. Меры защиты согласуются отдельно с ИБ на архитектурной сессии.
7. Раздел 8 (DoD) обязательно содержит статус двух гейтов деплоя: модель залогирована в MLflow, код в GitLab. Также в нём есть пункт «Согласование архитектуры с ИБ и архитекторами».
8. Для online-сервисов механизм деплоя в BRD не выбирается. Фиксируются характеристики нагрузки: latency, RPS, пики, синхронность.
9. Для batch-сервисов целевая платформа — Apache Airflow (DOC-03). Фиксируются расписание, объём за прогон и окно расчёта.
10. Для любого сервиса фиксируются требования к ресурсам: CPU, RAM, disk и отдельно GPU (тип, количество) — хотя бы порядок величины.
11. Готовый BRD публикуется в каталоге BRD (Google Drive), регистрируется в реестре BRD со статусом Draft и передаётся на согласование.

### 6.1 Пользовательские сценарии / User Stories

### 6.2 Функциональные требования к ML-компоненту (если применимо)

## 7. Нефункциональные требования (Non-Functional Requirements)

### 7.1 Производительность и масштабируемость
| Требование | Целевое значение |
|---|---|
| Latency (p50/p95/p99) | |
| Throughput (RPS/QPS) | |
| Объём данных (текущий/прогноз роста) | |
| Пиковая нагрузка | |
| Горизонтальное масштабирование | |

### 7.2 Доступность и надёжность
- SLA / uptime (например, 99.9%)
- RTO / RPO
- Disaster recovery план
- Стратегия деградации (graceful degradation, circuit breaker)
- Retry/timeout policy

### 7.3 Данные
- Источники данных и их владельцы
- Объём, скорость поступления, свежесть (data freshness)
- Качество данных: критерии валидации, обработка пропусков/выбросов
- Data lineage и версионирование (data + feature store)
- Схема данных / контракт данных (data contract)
- Retention policy

### 7.4 ML-специфичные требования
- Требования к обучающим данным (объём, баланс классов, разметка)
- Частота переобучения (retraining cadence) и триггеры
- Мониторинг дрейфа данных и модели (data drift, concept drift)
- Стратегия A/B-тестирования / shadow-деплой перед полным релизом
- Версионирование моделей и воспроизводимость экспериментов
- Требования к offline/online метрикам и порогам качества для деплоя
- Champion/challenger стратегия

### 7.5 Безопасность и приватность
- Аутентификация / авторизация
- Шифрование данных (at rest / in transit)
- PII-данные: маскирование, анонимизация
- Соответствие регуляциям (GDPR, 152-ФЗ и т.п.)
- Аудит доступа
- Модельная безопасность (adversarial-устойчивость, prompt injection — если LLM)

### 7.6 Наблюдаемость (Observability)
- Логирование (структура, уровень, хранение)
- Метрики (бизнес, системные, модельные) и дашборды
- Алертинг (пороги, каналы оповещения, ответственные)
- Трейсинг запросов (distributed tracing)

### 7.7 Совместимость и интеграции
- Внешние API/системы, с которыми интеграция
- Форматы обмена данными
- Обратная совместимость
- Поддерживаемые платформы/браузеры/устройства

### 7.8 Эксплуатационные требования (Operability)
- Требования к деплою (CI/CD, blue-green, canary)
- Требования к откату (rollback)
- Требования к инфраструктуре (compute, GPU/CPU, память)
- Стоимость эксплуатации (cost per inference, TCO)

### 7.9 Юзабилити и доступность
- Требования к UX (если есть интерфейс)
- Accessibility (WCAG и т.п.)
- Локализация/языки
