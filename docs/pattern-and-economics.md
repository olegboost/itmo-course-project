# Паттерн, модель на шаг и стоимость успешного результата

Продолжение раздела 4 паспорта («control layer, паттерн, экономика»). Control layer описан в [control-layer.md](control-layer.md), здесь описаны паттерн и экономика.

## 1. Паттерн: sequential pipeline с валидатором (BRD-04)

**Процесс одной строкой:** по транскрипту интервью с заказчиком собрать BRD по стандарту команды и опубликовать его в wiki.

**Почему именно этот паттерн.** Выбор следует из задачи, а не из наличия шаблона:

- **У BRD жёсткий стандарт команды** (DOC-12, шаблон из 13 разделов), и большая часть его правил проверяется кодом без модели:
  - все 13 разделов на месте;
  - в разделе 8 есть отдельные пункты про MLflow и GitLab и пункт про согласование с ИБ;
  - в подразделе 7.5 есть строка «меры согласовываются отдельно с ИБ»;
  - требования оформлены как FR-xx с Given/When/Then;
  - есть роли DevOps и ИБ;
  - каждому TBD соответствует открытый вопрос;
  - если в интервью звучал внешний LLM, он записан как риск.

  Это задача именно для «цепочки шагов с проверкой кодом между ними».
- **Раньше BRD, нарушивший стандарт, проходил дальше:** проверка считала только число разделов. Ошибку замечал человек уже после публикации. Теперь нарушение ловится до публикации и исправляется точечно.
- **Почему не другие паттерны.** Router не нужен: вход один (транскрипт). Supervisor с субагентами избыточен: этапы фиксированы и идут строго по порядку, координатору нечего решать. Agentic RAG в системе уже есть внутри шагов: интервьюер и писатель сами решают, идти ли в базу знаний.

**Цепочка (воркфлоу BRD-04):**

| # | Шаг | Кто выполняет | Что на выходе |
|---|---|---|---|
| 0 | Проверка потолков | код (*Check limits*) | Можно ли генерировать: попытки, число BRD за 24 ч, бюджет сессии |
| 1 | Писатель | агент *BRD writer* + инструмент KnowledgeBase | Черновик BRD в 3 части (разделы 0–5, 6–7, 8–12) |
| 2 | Валидатор | код (*Validate BRD*), решение — *Quality gate* | Список нарушений, каждое привязано к разделу. Дальше: публиковать, ещё раунд или отдать человеку |
| 3а | Перегенерация части | агент *BRD writer (regen)* + KnowledgeBase | Если пропал целый раздел, писатель пишет заново всю его часть. В запрос добавляется текст ошибки проверки («нет раздела 6…») |
| 3б | Исправление | LLM-цепочка *BRD fixer*, без инструментов | Если разделы на месте, но нарушают правила, переписываются только эти разделы |
| 4 | Повторная проверка | тот же код (*Revalidate*) → снова *Quality gate* | Весь документ проверяется заново. Это петля: не больше 2 раундов |
| 5 | Публикация | Drive API | Google Doc с ключом `appProperties.brd_key`, запись в реестр, уведомления |

Если на шаге 2 нарушений нет, шаги 3–4 пропускаются. В каждом раунде выполняется либо 3а, либо 3б: сначала восстанавливаются пропавшие части, потом правятся детали.

**Где предел паттерна.** Потолки прошлого занятия стали параметрами конструкции:

| Потолок | Значение |
|---|---|
| Шаги писателя на одну часть BRD | `maxIterations = 6` |
| Раундов исправления после валидатора | **2** (`BRD_REPAIR_ATTEMPTS = 2`) |
| Бюджет сессии | $1 |
| Попытки генерации на сессию | 2 |
| BRD за 24 ч | 5 |

**Что после предела.** Если после двух раундов валидатор всё ещё находит нарушения, прогон уходит в ручную очередь BRD-07 (`limit_type = validator`), а сессия получает статус `needs_review`. Заказчику приходит отдельное сообщение: «не удалось автоматически собрать документ по стандарту, черновик передан команде», без совета повторить `/done`. В лист `errors` пишется строка `brd_quality` с severity warning, без алерта саппорту. Третьего раунда нет: повтор после предела кормит разгон.

**Почему 2 раунда (уточнено 2026-10-14 по замечанию ревьювера).** Перегенерация — повтор класса 1: наружу ещё ничего не ушло, так что повтор безопасен. Раунд стоит $0.02–0.1 и остаётся под бюджетом сессии $1. Первый раунд обычно восстанавливает пропавшую часть, второй дочищает детали.

### Две ветки сбоя: плохой ответ модели ≠ сбой записи

Это разные события, и у них разные ветки (замечание ревьювера к позиции 5.2):

| | Плохой ответ модели | Технический сбой (LLM, Drive, сеть) |
|---|---|---|
| Где ловится | *Validate BRD* / *Revalidate* — документ нарушает стандарт | error-выход узлов: писатель, исправление, загрузка в Drive |
| Повтор | 2 раунда исправления, класс 1 (безопасно) | Загрузка: **без слепого повтора**. Перед единственным повтором документ ищется по `appProperties` |
| Если не вышло | Ручная очередь, сессия `needs_review` | Сессия возвращается в `active`, алерт саппорту |
| Заказчику | «Документ не собрался по стандарту, черновик передан команде» | «Техническая ошибка, отправьте /done через несколько минут». Если документ был составлен, но не опубликован: «текст сохранён, /done только опубликует его» |
| Журнал | `errors`: `brd_quality`, warning, без алерта | `errors`: `brd_generator`, error, алерт саппорту |

**Как сделана безопасная публикация.** Создание Google Doc — класс 3: повтор создаёт второй документ. Поэтому:
1. В метаданные загрузки пишется `appProperties: { brd_key: "<session_id>#<номер попытки>" }`. Номер попытки нужен потому, что у сессии законно бывает 2 попытки генерации.
2. Узел загрузки больше **не** повторяет запрос сам (`retryOnFail` снят).
3. Если загрузка вернула ошибку, ищем файл запросом `appProperties has { key='brd_key' and value='…' } and trashed = false`. Нашёлся — документ создан, хотя ответ потерялся: публикуем найденный, дубля нет. Не нашёлся — ждём 10 с и делаем **один** повтор.
4. Если и повтор упал, готовый текст BRD сохраняется в сессии (`brd_draft`), и следующий `/done` только публикует его, без новой генерации и новых денег.

Заранее выданный ID файла (`files.generateIds`) не подходит: Drive API не поддерживает его при создании Google-документов и при загрузке с конвертацией.

### Классы повторяемости шагов BRD-04

Классы: 1 — повтор безопасен; 2 — повтор безопасен при ключе идемпотентности; 3 — повтор с внешним побочным эффектом, требует проверки перед повтором.

| Шаг | Класс | Как повторяется |
|---|---|---|
| Чтение сессии, проверка потолков, `GET /key` | 1 | Можно повторять сколько угодно |
| Запись попытки, статуса сессии, черновика (Data Table upsert по `session_id`) | 2 | Ключ — `session_id`, повтор перезаписывает ту же строку |
| Писатель, перегенерация, исправление (LLM) | 1 | Наружу ничего не уходит. Ограничено раундами, `maxIterations` и бюджетом |
| Валидатор | 1 | Детерминированный код |
| Создание Google Doc | 3 → защищён | Без слепого повтора: поиск по `appProperties.brd_key`, затем максимум один повтор |
| Строки `brd_registry`, `brd_runs`, `manual_queue` (append в Sheets) | 3 | Не повторяются автоматически |
| Сообщения в Telegram (BRD-02) | 3 | Не повторяются автоматически |

## 2. Инструмент выбирает агент, а не ветка

- **В экспорте** (`workflows/BRD-04_brd-generator.json`) инструмент KnowledgeBase подключён к узлу *BRD writer* связью `ai_tool`. Ни одной if-ветки «если X, искать в базе знаний» нет. По экспорту нельзя заранее прочитать, будет ли поиск, сколько раз и с каким запросом.
- **В прогоне** решение видно в `intermediateSteps` писателя. Кроме того, BRD-04 сам пишет в лист `brd_runs` колонки `kb_calls` (сколько запросов) и `kb_queries` (какие именно, по частям). На разных транскриптах агент делает разные запросы: для online-сервиса — про чек-лист готовности, для К4 — про политику ИБ, для дубля — про реестр сервисов. Это и есть доказательство выбора по ситуации.
- **То же в BRD-03:** интервьюер сам решает, нужна ли база знаний на этой реплике. В cost-attack это было видно: 0–3 запроса в зависимости от сообщения.

## 3. Модель на шаг

Принцип «проектируем на топовой, запускаем на лёгкой» соблюдён на этапе разработки. Промпты писателя и исправителя, шаблон BRD, правила валидатора и транскрипты для проверки проектировались с топовой моделью (Claude Opus в Claude Code), а работают на моделях ниже. Отдельный проектный прогон BRD-04 на топовой модели не делался: он занял бы место в потолке «5 BRD за 24 часа» и ничего не добавил бы к серии из пяти прогонов на рабочих моделях.

Модели по шагам:

| Шаг | Модель | Почему |
|---|---|---|
| 1 и 3а. Писатель BRD и перегенерация части | `deepseek/deepseek-v4-pro-0813` ($0.66 / $1.98 за 1M) | Самый трудный шаг: свести длинный транскрипт и найденные требования в 13 разделов, ничего не выдумать и развести «сказано», «гипотеза» и «TBD». Ошибку по фактам валидатор не поймает, поэтому здесь нужна сила |
| 2 и 4. Валидатор и решение по раунду | код, без модели ($0) | Правила стандарта детерминированы. Модель добавила бы цену и случайность там, где нужен однозначный ответ «да/нет» |
| 3б. Исправление | `deepseek/deepseek-v4.1-flash` ($0.30 / $1.20 за 1M) | Узкая задача по явному списку нарушений: дописать недостающий пункт или строку. Факты уже в транскрипте, ответ короткий (только нужные разделы). Хватает лёгкой модели |
| Поиск в базе знаний (инструмент шагов 1 и BRD-03) | `openai/text-embedding-3-small`, 1536 (cloud.ru) | Задано размерностью индекса Pinecone. Смена модели означает переиндексацию всей базы знаний |
| Интервьюер (BRD-03, вне паттерна) | `deepseek/deepseek-v4.1-flash` | Короткие реплики по одному вопросу, важна скорость ответа в чате. За сессию 15–40 вызовов, поэтому цена вызова решает |

## 4. Стоимость успешного результата: таблица пяти прогонов

**Прогон** — один полный проход BRD-04 от транскрипта до опубликованного BRD или остановки по пределу. **Цена прогона** — фактический расход ключа OpenRouter за прогон: разница `usage` до и после, колонка `run_cost_usd` в листе `brd_runs`. Она включает все шаги паттерна: писателя, раунды исправления и сами запросы. Интервью в цену прогона не входит, это отдельный шаг процесса.

### Критерий успеха (записан до первого прогона 2026-10-11; 2026-10-14, тоже до прогонов, «одно исправление» заменено на «до двух раундов» вслед за изменением паттерна)

> **Прогон успешен**, если выполнены оба условия:
> 1. BRD опубликован, то есть прошёл валидатор (сразу или после не более чем двух раундов исправления);
> 2. при ручной сверке с транскриптом в BRD **нет выдуманных фактов**: цифр, имён, систем, статусов и решений, которых не было в интервью.
>
> Остановка по пределу (`limit_stopped`) или ошибка — неуспех. Колонка «ожидаемый результат» перечисляет, что именно сверять по каждому входу. Если там неверный факт (например, `[x]` у GitLab, когда кода в GitLab нет), это выдуманный факт и прогон неуспешен.

Если после серии захочется пересмотреть критерий, это новая серия из пяти прогонов.

**Пограничные места.** На критерий «нет выдуманных фактов» они не влияют, но записаны для занятия 10 (eval):

Содержание верное, но пометка завышает уверенность: подтверждённой гипотезой по правилам промпта считается только ориентир интервьюера, на который заказчик ответил «да». В прогоне 5 при этом верно стоят `[ ]` и открытый вопрос.
- Прогон 4: в раздел 3 добавлена вторая цель «доля руководителей, подтвердивших пригодность выжимки». Значения TBD, но в интервью её не было. Это предложение писателя, а не выдуманный факт.

**Вне серии:** строка `brd_runs` от 19:29 с `error: Сессия не найдена: PASTE_SESSION_ID_FROM_brd_sessions`. Это запуск *Manual test* с незаполненным `session_id` до начала серии: LLM не вызывалась, цена $0. В серию не входит.

Доля неудачных 0 % на пяти прогонах не значит «неудач не бывает». На пяти входах это значит только, что ни один вход серии не вывел писателя за стандарт. Цикл исправления в этой серии ни разу не понадобился: все пять документов прошли валидатор с первого раза.

### Находки серии

1. **Валидатор не видит пропавшие подразделы.** В прогоне 2 раздел 7 оборвался на 7.6, а валидатор это пропустил: он проверяет только наличие 7.5. Нужно добавить правило «обязательные подразделы шаблона: 5.1–5.4, 6.1–6.2, 7.1–7.9». Тогда такой документ пошёл бы в раунд исправления.
2. **Фактическая цена в 9 раз ниже оценки сценария.** Самое правдоподобное объяснение — кэширование промпта у DeepSeek: 11 вызовов писателя за прогон начинаются с одного и того же длинного префикса (системный промпт, шаблон, транскрипт), а вход из кэша стоит примерно в 30 раз дешевле. Это рычаг экономии «кэширование» из материалов занятия, и наша оценка его не учитывает. Значит, бюджет сессии $1 по оценке консервативен (срабатывает раньше реальных $1). Сверка: OpenRouter Activity за весь день показывает $0.19, что согласуется с $0.132 серии плюс вызовы вне серии.
3. **Пометка «подтверждена инициатором» ставится на неуверенные ответы** (прогоны 3 и 5). Это уточнение для промпта писателя.

Исправления 1 и 3 меняют паттерн. Если их внести, по правилу задания для новой версии понадобится новая серия из пяти прогонов (около $0.15).
