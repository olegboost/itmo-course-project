# Веха 4: eval-набор и регрессия — что сделать в n8n (ручной импорт)

Что и зачем — в [eval-suite.md](eval-suite.md). Новый воркфлоу **BRD-97** прогоняет набор из 13 кейсов через
настоящие BRD-03 и BRD-04 и пишет вердикты в лист `eval_results`.

**Порядок регрессии важен:** сначала прогон «до» на текущем промпте, потом изменение промпта, потом прогон «после».
Иначе сравнивать не с чем.

## Часть 1. Подготовка и прогон «до»

### Шаг 1. Лист и колонка

1. В таблице «BRD agent — logs» создайте лист `eval_results` с заголовками из `sheets-templates/logs__eval_results.csv`:
   ```
   run_label,run_at,case_id,type,judge,verdict,human_verdict,expected,pass_rule,output,session_id
   ```
2. В Data Table `brd_sessions` добавьте колонку **`brd_md`** (тип String). В неё BRD-04 сохраняет текст BRD
   тестовых сессий `eval-*`, чтобы код мог проверить разделы. У обычных сессий колонка остаётся пустой.

### Шаг 2. ID BRD-03 в `.env`

Откройте BRD-03 в n8n, скопируйте ID из адреса (`…/workflow/<ID>`) и впишите в `.env`:
```
WF_INTERVIEW_ID=<ID>
```
Затем:
```bash
python3 scripts/check_workflows.py
python3 scripts/deploy.py --dry-run
```
В конце не должно остаться `__WF_INTERVIEW__`. Предупреждение про `__CFG_ALLOWED_CHAT_IDS__` ожидаемо: список пуст, бот открыт.

### Шаг 3. Импорт

Как обычно: открыть → Cmd+A → Delete → ⋯ → Import from File → `build/…` → Save → **Publish**.

| Воркфлоу | Что изменилось | Проверить |
|---|---|---|
| BRD-04 | текст BRD тестовых сессий сохраняется в `brd_md`; ожидание перед замером цены — 60 с вместо 15 | credentials, как в прошлый раз |
| BRD-03 | новый вход *When called by eval*; ответ тестовым чатам `eval-*` не уходит в Telegram, а возвращается прогонщику (*Eval chat?* → *Eval reply*) | credentials |
| BRD-05 | тестовые сессии `eval-*` не получают напоминаний | — |
| **BRD-97** (новый) | прогонщик набора | Create workflow → Import → credential Google Sheets в *Append to eval_results*; Settings → Error workflow = BRD-00; Save. Публиковать не нужно, запуск ручной |

BRD-03 и BRD-04 обязательно **опубликуйте**: BRD-97 вызывает опубликованные версии.

### Шаг 4. Прогон «до»

1. BRD-97 → узел **Config** → `RUN_LABEL` = `до` (так и стоит).
2. **Execute workflow.** Займёт около 10–15 минут: два BRD по 3–6 минут плюс 60 секунд ожидания замера цены на
   каждый кейс B*.
3. Итог придёт в чат команды («Eval-набор: прогон «до»…»), строки — в лист `eval_results`.
4. Кейс **I8** судите вы: прочитайте `output` и впишите в `human_verdict` **pass** или **fail** по признаку из
   колонки `pass_rule` (бот не выдумал пунктов приказа ФСТЭК, сказал, что в базе знаний этого нет, или передал
   вопрос ИБ).

**Пришлите мне** выгрузку листа `eval_results` (CSV). Если какой-то кейс показал «(нет ответа)» или упал, тоже
пришлите: разберём до изменения.

Попутно для мониторинга (позиция 6.2) снимите скриншот одного execution BRD-04 из этого прогона: шаги, вердикт
валидатора, строка *Run row* с ценой.

## Часть 2. Изменение и прогон «после» (после вашей выгрузки «до»)

1. Я меняю промпт писателя и пересобираю файлы. Вы переимпортируете **только BRD-04**, затем Publish.
2. BRD-97 → **Config** → `RUN_LABEL` = `после` → Execute workflow.
3. I8 снова судите вы (`human_verdict`).
4. Пришлите выгрузку `eval_results`. Я соберу сравнение «до/после» в [eval-suite.md](eval-suite.md) и запишу каждое
   расхождение в [improvement-log.md](improvement-log.md).

## Что учесть

- **Потолки не отключены.** За прогон создаётся 2 тестовых BRD (B1, B2); два прогона — 4, это в пределах «5 тестовых
  BRD за 24 часа». Третий прогон в те же сутки упрётся в предел, и кейс B1 или B2 покажет `fail` по причине предела.
- **Кейс I9** создаёт строку в `manual_queue` и предупреждение в чат команды. Так и задумано: это проверка эскалации.
  Строку можно сразу пометить `resolved`, `resolution = eval`.
- После прогона BRD-97 сам закрывает свои тестовые сессии (статус `eval_done`).
